# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build, test, lint

```sh
make build               # produces ./bin/curio, ./bin/curio-daemon, ./bin/curio-mcp (go build cache decides staleness)
make test                # unit tests under -race; no network, no Ollama (then internal/insight/... again without -race: its grouping property tests skip under it)
make test-integration    # needs network: fetches live sites (tag `integration`)
make test-e2e            # builds curio-daemon (tag `e2e`: test timing via CURIO_E2E_INTERESTS), drives it through daemonctl + client against fake Ollama; also the daemon's tests in that build
make vet                 # go vet with the build tags
make lint                # the pinned golangci-lint (refuses other versions; `make tools` installs it)
make vulncheck           # govulncheck, pinned
make tidy-check          # fails if go.mod/go.sum aren't tidy
make fmt                 # go fmt + go mod tidy, under the go.mod toolchain
make tools               # installs the pinned golangci-lint and goose
make help                # full target list
```

Run a single test:
```sh
go test -race -count=1 -tags=sqlite_fts5,sqlite_json -run TestParseHTML_Basic ./internal/importer/...
# on arm64, also compile sqlite-vec's NEON kernels, as make does (x86 can't build them):
CGO_CFLAGS="-O2 -g -DSQLITE_VEC_ENABLE_NEON" go test -race -count=1 -tags=sqlite_fts5,sqlite_json -run TestParseHTML_Basic ./internal/importer/...
```

The build tags are mandatory; without them SQLite FTS5 is missing and `chunks_fts` virtual table creation fails. `make` already passes them. Never invoke `go build` / `go test` directly without `-tags=sqlite_fts5,sqlite_json` — the Makefile is the source of truth.

Cgo is required (sqlite, sqlite-vec). `CGO_ENABLED=1` is forced in the Makefile. On arm64 the Makefile also exports `CGO_CFLAGS` with `-DSQLITE_VEC_ENABLE_NEON` (keeping `-O2 -g`, extending a `CGO_CFLAGS` already set), so sqlite-vec compiles its NEON distance kernels; `.goreleaser.yaml` sets the same. A `go test` outside `make` on arm64 needs that `CGO_CFLAGS` (the second command above), or `TestVectorExtension_NEONOnArm64` fails; elsewhere the define doesn't compile (`<arm_neon.h>` is ARM-only). The daemon's "database ready" log line names sqlite-vec's version and build flags. See `docs/decisions.md` "sqlite-vec: NEON distance kernels on arm64".

## Tooling traps

- **Go version**: the `go` directive in `go.mod` (`go 1.26.8`) is the exact toolchain CI and releases build with. setup-go installs it from `go-version-file`, and the Makefile exports `GOTOOLCHAIN=go<directive>`, so every `make` target runs it too (the go command downloads it once). Bump the patch when `make vulncheck` flags the standard library; move to the next minor before the current line leaves support. `go mod tidy` under another Go version produces a different `go.sum`: use `make fmt` / `make tidy-check`, or `GOTOOLCHAIN=go1.26.8 go mod tidy`.
- **No `toolchain` directive**: golangci-lint takes it as the target version, so building on a newer toolchain than the `go` line makes modernize suggest APIs that vet's stdversion check then rejects. Move the `go` line instead.
- **golangci-lint** is pinned once, in the Makefile (`GOLANGCI_LINT_VERSION`, v2.12.2); CI reads it with `make -s golangci-lint-version`. It must be built with a Go minor at least the directive's, or it can't type-check the standard library it is handed (the official v2.12.2 binary is built with go1.26.2). `make lint` refuses any other version; `make tools` installs the pinned golangci-lint and goose.
- **govulncheck** (`make vulncheck`, pinned v1.8.0) runs in CI on every push and PR and in the release gate. See `docs/decisions.md` "Toolchain: the go directive is the build toolchain".

## Architecture in one screen

Three binaries:

```
curio     (CLI, cobra)   ──HTTP+JSON──►  curio-daemon  ──►  SQLite (~/.curio/curio.db)
curio-mcp (MCP sidecar)  ──HTTP+JSON──►       │             ├ FTS5 (chunks_fts)
browser   (curio ui)     ──HTML /ui/──►       │             └ sqlite-vec (chunks_vec)
                                              │
                                              ├─► Ollama at http://localhost:11434  (embeddings)
                                              ├─► Native fetcher (Go-native HTTP + Readability)
                                              └─► Optional web2md (Node subprocess)
```

`curio-mcp` (`cmd/curio-mcp`) speaks MCP over stdio to clients like Claude Code and forwards tool calls to the daemon over the same HTTP API the CLI uses; it auto-starts the daemon. See `docs/mcp.md`.

- Storage state lives under `$CURIO_HOME` (default `~/.curio`): `curio.db`, `content/<doc_id>/<extraction_id>.md`, `daemon.pid`, `daemon.start.lock`, `logs/daemon.log` (the daemon's JSON log, which it writes to stdout), `logs/launchd.err` (a launchd-run daemon's stderr: only a dying runtime's output), `.curio-meta.json`, `config.yaml`, `setup.json` (`curio up`'s memory of declined optional installs).
- **The marker is the home's embedding contract.** `.curio-meta.json` records `format` (`curiohome.CurrentFormat`, 2), the embedding model and `embedding_dim`, fixed at `curiohome.Init`; `curio up` creates a new home with the model it picked at the width it measured, and the daemon (and `daemonctl.Discover`) with `config.Default().Embedding` (`qwen3-embedding:0.6b`, 1024). `curiohome.Home.CheckEmbedding` refuses a marker without format 2 (`ErrLegacyHome`, checked first) and a `config.yaml` whose `embedding.model`/`dim` differ (`*EmbeddingMismatchError`), with the fix (`curio up --fresh`, or set them back); the daemon runs it after the lock and config, before binding or opening the DB, and `curio doctor` fails its home check with the same text. No migration code converts an old home. `sqlite.EnsureVectorIndex` sizes `chunks_vec` from the marker's width right after `MigrateWithHooks` (001 still creates FLOAT[768]; the step recreates it while empty, never rebuilds one holding vectors). Test databases take their width the same way (`sqlitetest.NewDB`, `sqlitetest.Width`).
- **Embedding drift.** `internal/drift`'s `Monitor` runs in the daemon: at start, every minute and after a rebaseline it reads the model's digest (`/api/tags`, `ollama.Client.ModelDigest`) and `/api/version` and records them in the marker at the first successful check. A later change is verified once, with the monitor's mutex released: `drift.Sampler` re-embeds up to 64 stored chunks (`ChunkStore.SampleChunks`: 16 documents' longest, 48 random documents, one chunk each) through `Indexer.EmbedChunks`, the one path every index embed takes, and compares each with its stored vector (bit-identical, or cosine ≥ 0.9999 and length within 1.4%). A sample that matches records the new build (INFO, no report). One that doesn't, or that the build can't embed (`drift.ErrUnverifiable`: wrong width, input too long, a 4xx other than 404/408/429), is reported as `embedding_drift` on `/v1/healthz` with its evidence (`verification`, worded once by `drift.Evidence.Detail`; a warning in `curio doctor`, `curio status` and the Status page, one WARN per distinct drift). Other failures retry after 15 min, doubling to 4 h, and report the change unverified from the third in a row; while a verdict is pending the last report stands. A verification a rebaseline, a record or another change overtakes is discarded, and at most 4 start in an hour (a build that keeps changing would otherwise re-embed the sample back to back; the cap is one WARN). It is not a job and ignores the queue gate. It never reindexes; `POST /v1/documents/reindex-all` for state `fetched` resets the baseline once every job is enqueued. After startup it is the marker's only writer. See decisions.md "Embedding drift: verified by re-embedding a sample".
- **One daemon per home.** The daemon holds an exclusive `flock` on `daemon.pid` for its lifetime and writes its own PID there (truncated on clean exit, never unlinked). It takes the lock before loading config or opening the DB, and binds its port before migrating or starting workers, so a second daemon, or one that can't bind, exits without touching the DB. Liveness is the lock, never `kill(pid, 0)`. From the bind on it answers as a **starting API** until migrations, dependencies and orphan recovery are done: every request gets 503 + `Retry-After` with a `urn:curio:problem:daemon-starting` problem (a dashboard page GET gets a 503 starting page instead), and `/v1/healthz` adds `pid`, `home`, `version`, `phase` (`initializing` | `migrating`) and migration progress. Then `api.Server.Ready` swaps in the full router on the same listener. Migrations run one at a time (`sqlite.MigrateWithHooks`) so progress reaches healthz and the log.
- The CLI and `curio-mcp` auto-start the daemon via `internal/daemonctl`: with the home's launchd agent loaded (`curio daemon install`, behind `internal/service.Manager`) they `launchctl kickstart` it and wait on the launched PID like a spawned child, asking the manager whether it still runs only while it doesn't hold the lock; otherwise (no agent, one not loaded, no GUI session over ssh, or `daemonctl.New`, which the e2e harness and curio-mcp's tests use) they spawn it. The flock stays the safety net either way. They confirm identity through `/v1/healthz` (`pid`, `home`, starting or serving), and `curio daemon stop` only stops the PID the lock holder recorded: through `launchctl kill SIGTERM` when the agent runs it, a direct SIGTERM otherwise. `EnsureRunning` waits on progress, not a fixed time: 15s of silence from our daemon (`StartTimeout`) fails with the log tail, and a daemon that keeps reporting it is starting gets up to 30 min (`ReadyTimeout`, then `ErrStillStarting`, never "failed to start"); `OnMigrating` lets the CLI print one stderr line. `curio-mcp` starts with `EnsureStarted` (returns at the first starting answer, so a migration never holds the MCP handshake) and gives each tool call 30s; `curio ui` does too, since a starting daemon serves the page that shows its progress. `daemon.start.lock` is held while starting, until the new daemon (spawned or launched) holds `daemon.pid`, and throughout `Controller.Install`, `Uninstall`, a restart through launchd and `WithDaemonStopped(ctx, fn)` (boots the agent out, stops a daemon outside it, runs `fn` once nothing holds `daemon.pid`: `curio up --fresh` moves the home in `fn`), so no auto-starter starts a daemon in the middle of one. `Install` asks `service.Manager.Preflight` first (root, a program launchd can't run, no GUI session as `service.ErrNoGUISession`) and stops nothing for an install that can't happen; `launchctl print`'s exit 112 for an installed agent is `Status.NoGUISession`, which `curio daemon status` and doctor word as "no GUI login session (ssh); curio commands start the daemon themselves". The auto-discovery picks `curio-daemon` from the same directory as the `curio` binary, override with `CURIO_DAEMON_BIN`.
- The daemon listens on loopback only (`127.0.0.1:8765`; `daemon.listen` must be a loopback host). The API has no auth: it trusts local processes, and its middleware shuts out browsers. Requests are rejected unless `Host` is a loopback name on the bound port (stops DNS rebinding), rejected if they carry a foreign `Origin`, a change (non-GET/HEAD/OPTIONS) carrying `Sec-Fetch-Site` is rejected unless it is exactly `same-origin`, and bodies must be `application/json` (1 MiB cap, 32 MiB for import). The dashboard (`/ui/`, see below) is the one browser client, admitted because it is same-origin. See `docs/decisions.md` "Local API".
- SIGINT, SIGTERM and SIGHUP all shut down gracefully (5s HTTP + 15s worker drain; the agent's `ExitTimeOut` is 25s and daemonctl waits 30s, a chain a daemonctl test asserts). There is no config reload: restart the daemon (`Controller.Restart`, `kickstart -k` under the agent). The daemon exits 0 when a signal stopped it (even if its shutdown ran over), when another daemon already holds the home's lock, and when it refuses to start for a cause only a fix clears (a `refusal` in `cmd/curio-daemon`: a home it can't open, a config.yaml that doesn't load or validate, a home `CheckEmbedding` refuses, a vector index of another width; logged once at ERROR); 1 for anything else (a taken port, a DB it can't open or migrate, a crash), which the agent's `KeepAlive {SuccessfulExit: false}` restarts every 10s. So `config.Validate` must reject whatever the daemon would refuse only after binding (base URLs through `ollama.ValidateBaseURL`, web2md without a bin).
- **`curio up`** (`internal/setup`, `internal/cli/up.go`) is six steps built in `steps()`, in order: machine, ollama, models, home (+ config.yaml), daemon, import. The import step acts only for an empty library or `--import chrome[:<profile>]|safari|firefox|html:<file>`: it counts each source's new bookmarks with `POST /v1/bookmarks/import` and `dry_run` (writes nothing; answers `new_urls`), offers `brew install yt-dlp` for new YouTube videos then restarts the daemon and checks healthz `youtube_fetcher`, estimates (setup/estimate.go), sets pace and keep-awake in one `PUT /v1/queue`, and sends through `importer.Send`; the hand-off names `curio status --follow`. A `Step` has a read-only, bounded `Check` (a `Result`: OK/Warn/Fail, detail, a `Fix` with the exact argv of every command, or a `Hint`) and an `Apply`. The runner checks every step first (the plan), stops before applying anything on a blocker (a Fail with no fix), and then re-checks, confirms, applies and re-checks each step; nothing records progress, so a rerun resumes. `curio doctor` renders `Runner.Checks()` (the same checks) plus its own. The root's hook skips `Discover` for commands annotated `ownsEnvironment` (`up`, `doctor`, bare `curio`): Discover would create a default home. They build their environment with `daemonctl.Connect(home, cfg, url)` once the home exists. config.yaml is written once when absent, never edited; a new home's width is measured with one embed after the pull. Dependencies are injected (`setup.Deps`, the CLI's `deps`): `Probe` (sysctl/statfs/ioreg on darwin), `Installer` (Homebrew), `UI` (huh on a terminal, a line prompter when `TERM=dumb`/`ACCESSIBLE`, none without a terminal), `Connect`, `Sources` (`importer.Discover`); tests use `internal/setup/setuptest` (scripted UI, fake installer, probe, Ollama, scriptable `Source`, and a fake daemon a test binary becomes via `RunDaemonIfAsked`) and never run brew, launchctl, open or ollama. No test reads real browser files: every `setup.Deps` built in tests sets `Sources`, and the TestMain of internal/cli, internal/setup and test/e2e runs under `setuptest.WithoutBrowsers` (CURIO_CHROME_DIR, CURIO_SAFARI_DIR, CURIO_FIREFOX_DIR at an empty dir). depguard keeps setuptest out of production and `charm.land` inside internal/setup. A prompt left unanswered is `setup.ErrAborted`, which `cli.Run` exits 130 for.
- Keep-awake (`curio keep-awake on`, a `queue_settings` column, not config.yaml): `internal/keepawake` runs `caffeinate -i -w <daemon pid>` while it is on, the queue isn't paused, `pmset -g ps` says AC power, and jobs of the pools' kinds are pending or running. A schedule-closed queue keeps the hold; with it off, nothing runs.

GET-only pages under `/ui/` on the daemon's own port (`/` redirects there; `daemon.ui: false` turns them off; `curio ui` opens them); what they change (refetch, reindex, rebuild, the queue's controls, a failure group's refetch through `POST /v1/documents/refetch-all`) goes through `/v1`, sent by the pages' own `internal/ui/static/actions.js`. Search is the home, at `/ui/` (`/ui/search` answers 302 there with its query), then the Library, with its Failures tab at `/ui/failures` (a view of the Library under its navigation item, not a fifth one), the Interests, and Status at `/ui/status`. User doc: `docs/ui.md`; design: decisions.md "Dashboard: server-rendered pages in the daemon (phase 1)", "Dashboard: formatting budgets for stored markdown", "Dashboard: a design language under the CSP", "Dashboard: search is home, the Overview becomes Status", "Dashboard: actions through /v1, sent by a first-party module", "Dashboard: the Failures tab", "Interests page by offset within a run" and "Search pages by offset within a fixed-depth pool". Rules future changes keep:

- `/ui` routes are GET only (`TestDashboard_GETOnly`), and every `/` and `/ui` response carries the strict CSP, nosniff and no-referrer (`TestDashboard_SecurityHeaders`, which needs a sample request for each new route). Another site's subresource request for a page is refused (`isolateDashboard`).
- No inline script, style, event handler, `hx-on`, `hx-vars` or `javascript:` in templates (`TestTemplatesHaveNoInlineCode`). Links are built in Go (`internal/ui/links.go`), never in a template.
- A conversion to `template.HTML` (or any html/template trusted type) happens only on the markdown sanitizer's output (`TestTrustedHTMLOnlyFromTheSanitizer`). Markdown: goldmark without `WithUnsafe`, then link resolution against the document's URL (links, images and autolinks keep only http(s) URLs with a host, and mailto), then bluemonday (which requires the host again).
- Stored markdown is formatted only within the budgets in `internal/ui/budget.go`, checked before goldmark parses it, because some shapes cost goldmark the square of their size in time or memory (`TestMarkdown_OverBudget` renders each at 1 MiB; `TestMarkdown_JustUnderBudget` holds the worst within the budgets to a time and an allocation bound). Each shape budget overestimates goldmark's work, never underestimates it. Links and images are charged as stored, every one, before they are resolved, and goldmark's HTML is capped (`maxHTMLBytes`). Every render is also held to `maxFormatTime` (2 s) and `maxFormatAlloc` (1 GiB), checked from goldmark's extension points (`stopParser` first at every inline trigger, `stopReader.PeekLine`, the link transformer, `htmlWriter`); a failed check panics with its `*budgetError`, which only `format` recovers. A text over a budget or limit is shown as stored. GFM's Linkify stays out (its regexp scans escape the inline budget). A new goldmark extension's inline trigger characters go into `markup` and `stopParser`'s triggers (`TestMarkup_CoversInlineTriggers`); a goldmark upgrade re-measures those tests and must keep `TestMarkdown_FormatsAfterAStop` passing (an unwound render leaves goldmark reusable). Tests of the budgets alone use `newBudgetRenderer`, which relaxes the time limit.
- Remote images stay off by default (`?images=1` or `ui.load_remote_images`, and only then a CSP with `https:`).
- htmx is vendored and pinned by SHA-256 (`TestHTMXIsPinned`), with `allowEval: false` and `includeIndicatorStyles: false`.
- Changes go through `/v1` as JSON sent by `actions.js` with default-mode `fetch`, never form posts (`Referrer-Policy: no-referrer` makes browsers send `Origin: null` on those), and are `Sec-Fetch-Site: same-origin`. Search's pages are `?page=` 1-10 (`ui.SearchPageSize` 10, never `search.default_k`): an `hx-boost` wrapper swaps `#results` like the box, the box (`replace`) and the pager (`drop`) share one `hx-sync` on `.search-page`, the form holds no page, and a page past the last is a 200, where the interests' is a 404. ## State machine, briefly

This catches people:

**Jobs**: `pending ↔ running → done | failed`. `failed` is terminal — won't retry. `ClaimNext` counts the attempt. `MarkDone`, `MarkFailed`, `Requeue` and `Defer` only move a `running` row (`store.ErrNotRunning` otherwise). `Defer` sends it back to `pending` until a given `run_after`, with the attempt refunded and why it waits as `last_error`. `last_error` is a failed job's error; on a pending or running job it is the error the retry retries after or what a deferral waits for (`waiting for …`), and `MarkDone` clears it. The `run_after` column on a failed row is stale data from the last retry cycle (we update status + last_error but not run_after at terminal transition). The CLI hides `next_attempt` for failed/done rows for that reason. Only finished (done/failed) jobs can be pruned or deleted.

- **Interrupted** (the handler returned while the worker's context was cancelled, i.e. shutdown): requeued with the attempt *refunded*, whatever error the handler returned. Queue writes use a detached, 10s-bounded context, so outcomes still get recorded during shutdown. A handler that finishes during shutdown is `done`.
- **Orphaned** (left `running` by a daemon that died): at startup `Worker.RecoverOrphans` requeues it with the attempt *kept*. Once attempts are exhausted it goes `failed` and runs the permanent-failure hook. This is what stops a job that crashes the daemon from looping forever. **A `cluster` job gets one attempt**: every rebuild error is permanent (the engine counts it in `insight_state`, and the scheduler retries after its backoff), so one claimed with `Attempts > 1` is an orphan: the handler records it as one failed rebuild (`Rebuilder.Abandoned`: its running runs failed) and runs nothing, and the cluster pool's hook does the same for an orphan out of attempts.
- **Deferred** (the handler returned a `jobs.DeferError`: held back without a verdict, by a hold curio keeps itself or one an upstream names the end of, such as Jina's block of a site; the fetch handler makes one from a `fetcher.DeferError`): `Defer` puts it back until the hold ends, `run_after` clamped to [now+1s, now+24h], with the attempt *refunded*, `last_error` `waiting for <reason>` and no hook. Only while the job is under a day old (`deferralBudget`, from `created_at`); after that a deferral fails the attempt like any error. The worker checks done, then interrupted, then `ErrPermanent` (which wins over a deferral), then deferred. Defer signals no wakeup: idle polls find the job when it comes due. See decisions.md "Waiting is not failing: jobs curio didn't send are deferred".
- A handler or hook panic is recovered and fails the job permanently (`last_error` starts with `panic:`).
- **Queue gate**: a `pending` job is claimed only while the gate admits it. Every worker asks its `jobs.Gate` (the daemon's `jobs.QueueGate`) before each claim: paused, outside the daily schedule, or at the throttle's cap (gentle: 4 fetch, 1 index) holds claims back; running jobs are never interrupted. The settings are the one-row `queue_settings` table, read once at startup (unreadable = the daemon won't start) and written only by `QueueGate.Update`, which `PUT /v1/queue` (`curio pause|resume|throttle|schedule`) drives.

**Documents**: `pending → fetched | failed | dead`. The `failed`/`dead` transition is driven by the `jobs.OnPermanentFailure` hook (`PermFailHook` — receives the cause error) — when a fetch or index job permanently fails, the worker calls the hook, which records why in `documents.failure_cause` through `DocumentStore.MarkFailed`: `fetcher.FailureCause` of the error for a fetch, `index` for an index job. `MarkFailed` derives the state from the cause: `dead` exactly for `dead_link` (the error wraps `fetcher.ErrDeadLink`: hard 404/410 or a detected soft 404), `failed` for every other. Without this hook, docs would stay `pending` forever even after their jobs gave up. The cause is set exactly when the doc is failed or dead; `MarkFetched`, `ApplyFetch` and both refetch paths clear it in the statement that moves the doc on. `refetch` flips the doc back to `pending` and enqueues a fresh job (new attempts counter) in one transaction (`DocumentStore.RequeueFetch*`), so a doc is never left pending without a job. Refetching a `dead` doc is refused with 409 unless `--force` (`?force=1`), and `refetch --all` skips dead docs unless `--state=dead` is explicit. `curio refetch --all --cause <cause>` (`?cause=`) refetches one cause of failures (`dead_link` needs `--state dead`); `GET /v1/failures` counts them by cause with their top hosts. A `failed` or `dead` doc keeps its last extraction and chunks, but BM25 and vector search (so `/v1/search`, `search_bookmarks` and find-related) leave it out; a refetch that succeeds re-indexes it and brings it back.

## Fetcher fallback policy

Why a fetch failed is `fetcher.FailureCause(err)` (`internal/fetcher/cause.go`), which the permanent-failure hook stores: a new sentinel or failure path must be placed in its list.

`internal/fetcher/native.go` falls back to Jina Reader (`r.jina.ai`) only when the original error wraps `ErrLoginWall` or `ErrAntiBot` (or a PDF the local extractor couldn't read). Hard errors (404, DNS failures, timeouts) return directly — Jina can't help and burning rate-limit budget there gets us 429'd on the calls that would actually benefit. If you're tempted to widen the fallback, read `docs/decisions.md` under "Fallback strategy" first.

Jina requests identify as curio (`jinaUserAgent`), never as Chrome and without the browser headers: r.jina.ai's Cloudflare answers a browser User-Agent with a managed challenge (403). Jina calls from all fetch workers share one limiter (20/min, or 200/min with `fetcher.native.jina_api_key` / `CURIO_JINA_API_KEY`, sent as a bearer token) and one cooldown that a 429 extends, and that a Jina 403 with `cf-mitigated: challenge` extends by its `Retry-After` or 10 minutes (`jinaChallengeCooldown`), warning once per pause (`cooldown.extend` reports whether it started one): waited out inline up to 30s; a longer one defers the fetch until it ends (`*fetcher.DeferError` around a retryable 429 carrying the time left), the whole fetch running again then. Each Jina request also takes its site's turn (`sitePacer`, `internal/fetcher/sitepace.go`): a site is the registrable domain (`siteOf`, `publicsuffix.EffectiveTLDPlusOne`; the host itself for an IP or a name without one), paced at `fetcher.native.jina_site_requests_per_minute` (default 6, `DefaultJinaSiteRequestsPerMinute`), key or not. `awaitJina` clears a request in this order: the shared cooldown's pre-check (so a held request spends no turn), the site's turn (waited up to 30s, else a `DeferError` "a turn at Jina Reader for <site>", with no request, token or health record, whose Untils are spread an interval apart after those handed out), `pace`, a send-time guard that spaces the site's sends an interval apart whatever the limiter's queue did, and the site's block once more. In-fetch retries take turns too. Don't swap the pacer for a `rate.Limiter` per site: deferred pages would come back in a herd or starve (decisions.md "A site's block is not its pages' verdict"). The GitHub fetcher pairs its limiter and cooldown the same way (2-minute cap, then deferred). Both go through `pace`, which checks the cooldown twice: before queueing in the limiter, so a cooldown already past the inline cap defers at once without waiting for (and spending) a token, and again after the token is granted, so a 429 that arrived while the call was queued is still seen. An answer that was sent is never itself a deferral, except Jina's block of a site (below), which names when Jina reads the site again and decides nothing about the page: GitHub's long-`Retry-After` 429 and a Jina challenge fail their attempt. A Jina 429, though, is retried inside the fetch (`tryJina`) after the cooldown it set, so when that cooldown outlasts 30s the retry is held and the fetch defers (a 429 on the fetch's last Jina try fails it). Origin requests are capped at 2 in flight per host (`hostGate`); the slot is never held while waiting on Jina, and the host cache is re-checked once a slot is acquired.

`ErrAntiBot` wraps HTTP 403 and 503 (except after a redirect the redirect verdicts judge, below), a challenge or block page served with a 2xx (`challengeTitleRE`, or `challengePhrases` on a page of 2 KiB or less), and a 403/503 error page whose status is hidden (`errorPageTitleRE`, or an S3/GCS `AccessDenied` body on a short page); an error page naming another 5xx is `errServerErrorPage`, retryable and never sent to Jina (`errJinaTargetTrouble` in a Jina answer). The Native fetcher also sends origins Chrome-like headers (`Sec-Fetch-*`, `Sec-Ch-Ua-*`) to reduce false-positive bot blocks.

The chrome backend (tls-client) gives portless `http://` requests and every redirect hop an explicit `:80` (`pinPlainHTTPPort`, `chromeCheckRedirect`) because tls-client keys cached transports by `host:443` whatever the scheme; the pin never reaches Host, Referer, `finalURL` or error text, each hop takes its Host from its own URL, and a hop without a host is refused (`http: no Host in request URL`) rather than dialed on the local machine. Tests route chrome dials through `newRoutedChromeRT`; see decisions.md "Chrome backend: plain http carries an explicit :80".

Status classification is shared by all HTTP fetchers (`internal/fetcher/errors.go`): every HTTP failure carries a `*HTTPStatusError` (status, the URL that answered, `Retry-After`). 408/421/425/429 and 5xx except 501/505 are retried; every other status is a `PermanentError`. Native's policy (403/503 → `ErrAntiBot` unless a redirect verdict holds, see below; 404/410 → `ErrDeadLink`) runs before that rule. Error text quotes at most 512 bytes of a response body.

Every response body is capped at 32 MiB after decompression (`maxResponseBytes`; Native through the `limitBodies` transport decorator, GitHub via `readLimited`, Web2MD on its stdout). Overflow is a permanent `ErrTooLarge`: never Jina, never host-cached. A PDF over the cap still goes to Jina without being read further.

Subprocess fetchers (Web2MD, YouTube) run through `runCapped`: own process group, killed as a group on timeout or cancel, stderr capped at 64 KiB. At most 2 yt-dlp processes run at once (`YouTubeOptions.MaxConcurrent`). Their tests re-exec the test binary as the fake tool (`TestMain` + `CURIO_FAKE_TOOL`); don't write shell scripts.

YouTube (yt-dlp) specifics, each with a 2026-09-26 entry in decisions.md:

- `--sub-langs` defaults to `fetcher.DefaultYouTubeSubLangs` (`en,en-(?-i:[A-Z]{2})`; config leaves the key empty). Every matched track is one caption request: `en.*` also matched YouTube's `en-<source>` machine translations, one per uploaded caption language, and drew 429s.
- `--ignore-errors`: a caption track that fails to download is a `WARNING:` line, not an aborted video. A video left without a transcript is a `Partial` result (description only) whose `PartialReason` quotes yt-dlp and is stored as the extraction's `error_message`; the fetch succeeds and indexes, and `curio refetch <id>` retries the transcript.
- Any `HTTP Error 429` in yt-dlp's stderr (ERROR or WARNING) extends a 2-minute cooldown shared by every YouTube fetch. `Fetch` checks it through `pace` (nil limiter) before and after taking a yt-dlp slot: up to 30s is sat out, longer defers the fetch until the cooldown ends (`*fetcher.DeferError` around `*HTTPStatusError{429}`), without running yt-dlp. A run that met the 429 itself fails its attempt.

`ErrDeadLink` (404/410, soft-404 titles, redirect-to-homepage, redirect onto another site's landing page; the two redirect rules whether that page answered 2xx, 403 or 503) is always wrapped in a `PermanentError`, never goes to Jina from the origin, and is deliberately NOT host-cached (a dead path says nothing about the host).

Every page that comes back, from the origin or from Jina, is judged by one function, `judgePage`, in this order: dead link (with detection on: homepage, another site's landing page, not-found title) → bot challenge → error page → login wall by redirect → no article → thin (< `minArticleBytes`, 500 bytes) → login title. The soft-404 check runs BEFORE every login-wall check — order matters, thin tombstone pages would otherwise classify as login walls and leak to Jina. A not-found title is a whole template (`soft404TitleRE`: anchored at both ends, a site's name allowed before or after a spaced separator or as one word before a colon, explicit word lists whose every word has a row in `TestSoft404TitleRE`), read with its spaces made plain whether or not Readability found an article, so a headline that discusses a 404 is no verdict, though a title of a template and site names alone is, and so is a headline whose subtitle follows a spaced dash or that opens with the not-found sentence (decisions.md "Soft-404 titles: whole templates, not phrases"). `loginPathRE` matches a whole path segment (`/login`, `/Login.aspx`), never a slug like `/login-with-oauth`. A redirect onto another site is no verdict by itself (`looksLikeLandingPage` needs the source to name a page and the destination to keep none of its words and name no page of its own): another site's landing page is a dead link, another site's login page (path or title) is `errOffsiteLoginWall`, a `PermanentError` that never goes to Jina or the cache, and anything else is judged like any page and stored without Jina when it passes. A 403/503 from the origin gets the same URL rules before it is classified (`statusFailure` → `judgeRedirect`): a redirect onto the homepage or another site's landing page (detection on) or onto another site's login path is that verdict, a `PermanentError` still carrying the `*HTTPStatusError`, never `ErrAntiBot`, never Jina, never cached. Jina answers have no final URL, so no redirect rule fires on them. See decisions.md "Cross-site redirects: judged where they land".

Jina answers 200 whatever the target served, so its answer is judged before it is stored (`judgeJinaAnswer`): first the target status from its `Warning: Target URL returned error <code>` line (404/410 → dead link, final and uncached, or retryable and uncached with dead-link detection off; 403/503 → anti-bot; the other statuses `retryableStatus` retries, 408/421/425/429 and 5xx except 501/505 → retryable and uncached; any other status, 501/505 included → rejected), then its CAPTCHA warning (anti-bot), then `judgePage` with no final URL. A rejected answer (`errJinaRejected`) costs one Jina request, is never retried in-fetch, and counts as "Jina answered" when the fetch settles. The target's status is a `targetStatusError`, never an `*HTTPStatusError`, which is Jina's own status and drives its 429 cooldown. A Jina answer's `FinalURL` is the requested URL: `URL Source` only echoes the request. See decisions.md "Jina answers are judged like the origin's pages".

Jina's own non-2xx answers are read up to `errorBodyDrain` (4 KiB) and quote its reason (`jinaReason`: a JSON `message`, after its `name`, or a first line like `AbuseAlleviationError: …`; never an HTML page) after the status. An `AbuseAlleviationError`, with a 403 or a 429, is Jina's block of a site's keyless reads for now (`*jinaSiteBlock`, `errJinaSiteBlocked`), told apart before the refusal rule: its end comes from Jina's JavaScript date (`jinaSiteBlockDefault`, 1 hour, when unreadable; clamped to [`minJinaSiteBlock`, `maxJinaSiteBlock`] = [1 min, 24 h]), it is recorded under `siteOf` the domain it names (the target's site when none) and only ever extended, and the page that got it and every later page of the site are deferred until it ends ("Jina Reader's block of <site> to lift"; later pages send nothing: `jina: not sent, Jina Reader blocks <site> until …`), one WARN per block. It is never `jinaAnswered`, never cached, never extends the shared cooldown and is never retried in-fetch; `FailureCause` gives `rate_limited` once a day of waiting runs out. Jina's own 403 otherwise: a challenge (`cf-mitigated: challenge`) pauses Jina; one whose reason names the target's host (`namesHost`, a whole hostname) is a refusal (`errJinaRefused`), a verdict like its other deterministic 4xx (400, 404, 410, 422, 451); any other 403 (bare, naming another host, Cloudflare's block page) is no verdict, retryable and uncached, so a block of curio itself can never fail documents for good. `jinaAnswered` is `errJinaRejected` or `errJinaRefused`; a refusal is never retried in-fetch and `settle` decides the rest. See decisions.md "Jina refusing a target is a verdict" and "A site's block is not its pages' verdict".

Jina's health (`healthTracker` in `internal/fetcher/health.go`, read through `Native.JinaHealth`): each Jina request (not a cancelled or never-sent one) is one `CallClass`, `ok`/`judged`/`refused` healthy, `challenged`/`forbidden`/`rate_limited` (a 429, or a site block whatever its status)/`auth`/`server_error`/`network` failures (`jinaCallClass`), counted in 15 one-minute buckets. The state is `disabled` → `failing` → `paused` (the Jina cooldown) → `idle` → `degraded` (a quarter of the window failed) → `ok`, first match. `failing` is set when a recorded failure extends a streak with no healthy answer that spans 2+ target hosts and has 5 failures or 30 minutes; it lasts until the next healthy answer. Only failing's transitions log (one WARN `upstream failing`, one INFO `upstream recovered`, under the tracker's lock). It surfaces as `upstreams` on `/v1/healthz` (`api.Deps.Upstreams`; `status` stays `ok`; `site_pauses` lists the site blocks in effect, which leave the state alone), a `jina` check in `curio doctor` (✗ failing, ! degraded/paused, with a hint for the dominant failure class, and the blocked sites named, at most 3), and one warning line in `curio status` while failing. In memory, reset on restart. See decisions.md "Fetch upstream health: Jina's calls are tracked and reported".

`ErrTLSCertificate` (a server certificate that fails verification: expired, not yet valid, wrong name, unknown authority) is a permanent origin failure: never Jina, never host-cached, and the doc goes `failed`, not `dead`. Each backend maps its own TLS stack's `CertificateVerificationError` (uTLS's is a distinct type from crypto/tls's). Other TLS failures (alerts, resets mid-handshake, a non-TLS answer) stay retryable, and a certificate failure talking to Jina is Jina's trouble, retried as usual. See decisions.md "TLS certificate failures are permanent, never Jina, never host-cached".

A fresh entry in the in-memory host-failure cache (`hostFailureCache`, 15-min TTL, on the fetcher's injectable clock) holds the host's other pages without an origin request (`pastCachedHost`): an unreachable entry fails them with a `PermanentError` wrapping the sentinel (Jina can't reach the host either); an anti-bot or login-wall entry sends them to Jina without an origin slot (checked before `hostGate.acquire` and after, released before any Jina wait), and Jina's answer decides each page alone, final for a verdict about the target, retryable or deferred for Jina's trouble or a hold; with Jina off, it defers them until the entry expires ("<host> to be tried again: …"), never a `PermanentError`. A page that skipped the origin never writes or refreshes an entry. The *first* failure for a host stays retryable; it's what populates the cache, and the entry quotes the origin's own answer (`settle` stores `originErr.Error()`), which later pages' `(cached: …)` repeats. Recovery is `curio refetch --all --state=failed` (or `--cause=…`, or per-doc `curio refetch <id|url>`). See `docs/decisions.md` "A site's block is not its pages' verdict".

Only host-wide verdicts are cached (`hostVerdict`): unreachable (NXDOMAIN, `ECONNREFUSED`, `EHOSTUNREACH` — not DNS timeouts or `ENETUNREACH`), anti-bot (a 403/503 no redirect verdict explains), and a redirect onto the site's own login page. They are keyed by the host that *answered* (the redirect target), never cached when Jina failed for its own reasons (429/5xx/timeouts/401/402, a 403 of its own that names no target: its CDN challenging curio, or any other refusal of curio; its block of the site) or reported a transient target status, only when Jina was off or gave a verdict about the target (a rejected answer, or a refusal such as a 403 naming the target's host). Only the origin's own verdict is cached (`settle` judges `originErr`); a Jina verdict never writes the cache. Page-level verdicts are never cached. Thin text, no article, a login title, and a challenge or 403/503 error page recognized in page content fail permanently once every configured extraction path has answered. A redirect onto the homepage or another site's landing page (dead link, detection on) or onto another site's login page (`errOffsiteLoginWall`: its path or title after a 2xx, its path alone after a 403 or 503) is final at once, without Jina. An error page naming another 5xx (`errServerErrorPage`) is retried and never sent to Jina. When the origin's error is a host-wide verdict from a redirect target that has a fresh entry, that entry holds the page as above (`pastCachedHost`, carrying the page's own origin error), writing nothing; a page-level verdict or a transient status from that host doesn't consult its entry. The cost of routing a cached host's pages to Jina: its answer has no final URL, so while the entry is fresh, a redirect onto the homepage or a landing page is caught only by a not-found title. See "Host cache: only host-wide verdicts, under the host that gave them".

## Fetcher routing

`$CURIO_HOME/fetcher_rules.yaml` (optional) routes URLs to fetchers — `host` / `host_suffix` / `host_in` / `{}` catch-all matchers, first match wins, hot-reloaded via throttled stat-on-dispatch (`internal/fetcher/rules.go`). Missing file = built-in defaults (github.com → github, youtube hosts → youtube when yt-dlp exists, everything else → the config default). Invalid edits keep the last good rules; unknown fetcher names skip the rule with a warning.

## Insight layer (M4)

Groups documents into labeled interests, and a large library's interests into areas (two levels; the run's `shape` is `areas` or `flat`), under identities that outlive rebuilds. The grouping sits behind `insight.Grouper` (`GroupInput{Points, Shape, Prior seeds, Split}` → `Grouping`); the shipped one is `LouvainGrouper` (`insight.NewLouvainGrouper`), and `FlatGrouper` wraps any `Clusterer` (`KNNGraphClusterer` stays as the quality harness's baseline). See decisions.md "Interests: two levels, stable identities, automatic rebuilds" and "Louvain: ours, warm-started; gonum as a test oracle".

- **The engine** (`insight.Engine.Rebuild(ctx, tenant, trigger)`), in order: the latest done run (the prior) → `DocumentVectors` (non-finite dropped; none with a prior keeps the prior, writes nothing and fails the rebuild, so the scheduler backs off instead of queueing it again) → `InsightStore.Changes` since the prior and `State` (a fresh rebuild owed) → the prior's assignments and groups → plan → `CreateRun` → `PreparePoints` → `Group` (warm from the prior's seeds when eligible) → `MergeNearDuplicates` → `Centroids` → `AssignStrays` (member, loose fit or unsorted) → `Carry`, areas then interests (a group inherits its predecessor's ID and label by the 70% rule; others get new UUIDs) → label → `CommitRun` → prune (`PruneRunsExcept`, `TrimLineage`, `PruneRetired` past `RetiredRetention`, 180 days; each best effort, one WARN) → the placement sweep. Every failure but a cancellation counts in `insight_state` (`RecordFailure`, failing the run in the same transaction when there is one; WARN "interests: rebuild failed" with failures and retry_at); a cancelled run is failed on a detached 10 s context and counts nothing. One INFO line, "interests rebuilt", carries counts, timings, `placed_after`, and `embeddings_drifted=true` for a run built while drift was reported.
- **Fresh or warm.** Warm-eligible: a prior made by this grouper with byte-equal params (the grouper's constants plus `center`; `Engine.ParamsChanged` is the one comparison) and no fresh rebuild owed. The recorded kind is fresh unless warm-eligible, the shape held and the prior seeded some point. Carry-over runs either way. changed = `Changes(prior).Total()`: added (fetched, `indexed_at` ≥ the prior's `vectors_read_at`, unassigned), left (assigned, now pending, failed or dead), deleted, reindexed (assigned, indexed again since); derived, so a restart keeps it, and a document the prior couldn't group (no chunk, non-finite) never counts. **Split check**: T = `insight.Threshold` = max(5, ⌈5% of the prior's documents⌉); a warm run splits when `changes_since_split` + changed ≥ 4·T, and a fresh or split run resets the count. Manual rebuilds don't force it (measured: it renames).
- **Storage** (migrations 016 and 017, `store.InsightStore`): `interest_runs` (one per attempt, `running → done | failed`, with trigger, kind, split_check, shape, grouper, params, `vectors_read_at`, mean and the outcome; the current grouping is the latest done run, which never changes), `interests` (identities, areas and interests, with the label; `retired_at`/`retired_run_id` once a run no longer holds them), `interest_groups` and `interest_assignments` (run-scoped, tenant through the run; one assignment per document with `fit`, `area_id` and warm-start seeds), `interest_placements` (documents placed between rebuilds, run-scoped), `interest_lineage` (kept/moved/split/merged, outlives runs) and `insight_state` (per tenant: `fresh_owed` `reindex`|`manual` with `fresh_owed_at`, `failures`, `last_failure_at`, `last_error`). `documents.indexed_at` (017) is when a document's vectors were written: `MarkFetched` sets it, nothing else. **`CommitRun` is one `BEGIN IMMEDIATE` transaction**: the `PriorRunID` check (`ErrConflict`), new identities, relabels, groups, assignments and lineage through prepared statements, retirement of every live identity the run doesn't hold, the run to done, the failures cleared, and for a fresh run the fresh rebuild owed cleared when owed at or before the run's `vectors_read_at` (a `reindex` one not when `ReadMidReindex`: the engine found index jobs left before or after it read the vectors, `Config.Indexing`). Vectors are float32 LE BLOBs.
- **The scheduler** (`insight.Scheduler`, daemon-only, none with insight off): checks every minute, at start (synchronously, before the API is up and any worker claims) and on every `Kick` (a rebuild requested, started or finished; a reindex-all), each check bounded by 30 s, and queues a `cluster` job (`jobs.EnqueueRebuild`) when no rebuild is queued or running; it is **due** (no done run and 20 fetched; a fresh rebuild owed against a done one; failures past their backoff; or `Changes(R).Total` ≥ `Threshold(R.NumDocuments)`; always with ≥ 1 fetched document); **not held** (no embedding drift reported; `RetryAt` = last failure + `RetryDelay`, 15 min doubling to 4 h, passed); **settled** (nothing indexed for 10 min, or due for 2 h, 30 min with no done run; a re-embedding's fresh rebuild only once no index job is pending or running and 10 min quiet, with no cap). Trigger: `first` > `reindex` > `params` > `auto`. States, first that holds: rebuilding, queued, held, failing, due, current, none; `unknown` before the first check, `off` (API) with insight off. When it became due is in memory only. Logs: "interests: rebuild due" and the WARN "interests: rebuilds held" once an episode, "interests: rebuild enqueued" each time. Its values are exported constants; `SchedulerConfig` shortens them in tests, and an e2e build reads `CURIO_E2E_INTERESTS` (`cmd/curio-daemon/schedule_e2e.go`; a release has no knob).
- **Placement** (`insight.Placer`): the index handler calls `Place` after `MarkFetched`; it mean-pools the document's chunk vectors (`store.MeanVector`, as `DocumentVectors` does), places it in the latest done run's space (interest at cosine ≥ 0.45, else Unsorted with the nearest's cosine) and writes one row guarded by "still the latest done run, not assigned, document exists" (`PlaceDocument`). Never fails the job: its own 10 s timeout, panics recovered, one WARN per run then DEBUG. `Sweep` (after each commit, and at the scheduler's start) places what the run neither assigned nor placed (`Unplaced`, `PlaceMany` ON CONFLICT DO NOTHING). Both hold while drift is reported or a `reindex` fresh rebuild is owed.
- **Fresh rebuilds owed**: `POST /v1/documents/reindex-all` (state fetched, ≥ 1 document) calls `OweFresh(reindex)` before enqueuing; `POST /v1/interests/rebuild?fresh=1` (`curio interests rebuild --fresh`) `OweFresh(manual)`, which never replaces `reindex`; a params change is derived, never stored.
- **Labels** (`labels.go`): only new groups, carried ones without a label, carried term labels when the LLM is wanted, and the smaller of two carried labels sharing a `LabelKey` in a scope (an area's interests, the areas, or all flat interests). Interests first, area by area largest first, each seeing its area's name and its siblings'; then areas, named from their interests' names and sizes. No two labels in a scope share a `LabelKey` (one function, shared with `quality`): a repeat is asked again once with `ClusterInfo.Taken`, then gets a term label that skips sibling words. A warm rebuild of an unchanged library calls no labeler.
- **LLM by default** (`insight.labeling = "llm"`). Needs a generation model in Ollama — the daemon **auto-pulls it** (`generation.auto_pull`, default true; the embedding model auto-pulls too via `embedding.auto_pull`), retrying with capped backoff (5s doubling to 5min) until Ollama serves it (`ollama.Client.KeepPulled`). Until the model is ready (or if it's unavailable / auto_pull is off), labeling **falls back to deterministic term labels**, so it stays zero-setup-safe. The fallback is decided per run (no startup ping): the first LLM failure that would repeat term-labels the rest of that run, and `insight.labeling_timeout_seconds` caps its LLM time, retries included. Set `insight.labeling = "terms"` to force it. Both Ollama clients (`internal/embedder`, `internal/generator`) sit on one `internal/ollama.Client`: base-URL validation, `Ping` (/api/tags model match), `Version`/`ModelDigest`, `EnsureModel`/`Pull`/`KeepPulled`, bounded `PostJSON`, and one sentinel pair (`ollama.ErrUnreachable`, `ollama.ErrModelNotLoaded`) that healthz maps to advice. Every `/api/embed` sends `truncate: false` and `keep_alive: "30m"`; a context-length 400 is `embedder.ErrInputTooLong` and a wrong-width reply `embedder.ErrWrongDimension`, both permanent index failures. Every `/api/generate` sends `think: false` and `num_ctx`. The writing model (`generation.model`) is never recorded in the marker: change it and restart.
- **Rebuild jobs**: a corpus-wide **`cluster` job on its own single-worker pool** (`jobs.NewPools`), **one attempt** (every rebuild error `ErrPermanent`; an orphan claimed again is recorded as abandoned, not run; see the job state machine), with no doc-state hook. Its payload is `store.ClusterJobPayload{Trigger}` (missing or unknown = manual), queued through `jobs.EnqueueRebuild` → `JobQueue.EnqueueOnce`: at most one pending cluster job per tenant (a running one doesn't count); the pending check is written `+tenant_id` so it seeks `idx_jobs_claim`, not the tenant's every pending job. The scheduler and `POST /v1/interests/rebuild` are the only enqueuers; the request skips the threshold, settle, drift hold and backoff, not the queue gate.
- Doc vectors come from `ChunkStore.DocumentVectors` (bulk mean-pooled per doc, single query) — do not loop `EmbeddingsForDocument`.
- **API**: `GET /v1/interests` (the run's top-level groups: areas with `children`, or flat interests; `level=interest` for every interest; `next` is the scheduler's snapshot, `InterestsState`, the same as healthz's `interests`: never a query per request; `api.Deps.Interests` is the scheduler, nil with insight off), `GET /v1/interests/{id}` (an area with its interests, or an interest's members then loose fits and its `new_members`; a retired ID is a 410 `urn:curio:problem:interest-retired` with its successors, mapped in `errorStatus`), `GET /v1/interests/unsorted` (with the `new` placed there), `GET /v1/interests/changes`, `POST /v1/interests/rebuild` (202 with the new or pending job's ID; `?fresh=1`; 409 when `insight.enabled` is off). `curio status` prints one interests line, `curio doctor` an interests check (! held or failing). Pages are by offset within a run; members' documents are read in one `GetByIDsWithLastError` per response. Config knobs: `insight.{enabled,center_vectors,labeling,labeling_timeout_seconds}` + `generation.{provider,model,base_url,timeout_seconds,auto_pull}` + `embedding.auto_pull`. `insight.{knn,min_similarity,min_cluster_size}` are deprecated: accepted with any value, ignored, one WARN at daemon start (`Config.DeprecatedKeys`).

## Conventions to preserve

- The CLI never echoes `tenant_id` to clients; tenant scoping is server-side. Single-tenant local installs use `store.LocalTenantID` (`"local"`).
- API list endpoints use keyset cursor pagination (`?cursor=...` / `next_cursor`), not offset: ordered by `(updated_at|created_at|saved_at, id)` DESC, with `store.PageKey` in the store and the row-value predicate that the list indexes (which end in `id`) serve. A cursor records its list's order when it isn't the default (bookmarks' `order=saved`), so one from another order is a 400. New list queries get a pinned plan in `plans_test.go`. Two exceptions page by `offset`, for numbered pages a keyset can't serve: the interests, within a run, whose groups and assignments never change after `CommitRun` (identities are stable across runs; a retired ID answers 410; decisions.md "Interests page by offset within a run"); and `POST /v1/search`, within the one fixed-depth ranking every request for a query gets (`total`, `capped`; offset + k ≤ 100, checked as a difference so it can't overflow), whose recomputed scores have no keyset (decisions.md "Search pages by offset within a fixed-depth pool"). A malformed offset is a 400, one past the end an empty page.
- Queued work returns `202`: `{job_id}` for single-target ops (refetch, reindex, interests rebuild), which clients poll through `GET /v1/jobs/{id}` (`curio jobs show <id>`); `{jobs_enqueued}` for the bulk refetch-all and reindex-all, which have no parent job and are watched through `GET /v1/jobs` or `/v1/stats`. Import is synchronous (`200`) and enqueues fetch jobs.
- Errors over the wire are RFC 7807 (`application/problem+json`).
- `curio docs` and `curio jobs` default to the happy-path view (`state=fetched`, `status=done`). `--failed`, `--all`, and explicit `--state`/`--status` widen.
- Both list views include the on-disk markdown path under `doc_id` so `cat`, `curio docs show`, and `curio refetch` are copy/paste-ready.
- Store SQL lives in constants and builders that `internal/store/sqlite/plans_test.go` also runs, pinning each hot query's index (curio never runs ANALYZE). A query or index change must keep its plan, or update the pin and `docs/decisions.md` "Indexes follow the queries".
- Every UPDATE sets `updated_at` itself; no trigger does. Triggers on `chunks` keep `chunks_fts` and `chunks_vec` in step, so never `INSERT OR REPLACE` into `chunks`. The schema version is goose's (`goose_db_version`); migrations don't record it.

## CI release flow

`ci.yml` runs on pushes to main and on PRs: `test` (ubuntu: tidy-check, build, vet, test, test-e2e, vulncheck), `test-macos` (macos-14, the release runner: `make test`), and `lint` (golangci-lint at the Makefile's pin, plus `make actionlint`). `v*` git tags trigger `.github/workflows/release.yml`, whose `ci` job calls `ci.yml` (`workflow_call`) as a gate: the `release` job `needs` it, so a tag whose tree fails any CI check never publishes. Only the release job gets `contents: write` and the tap PAT; it runs goreleaser (pinned exactly) → a binary tarball on GitHub releases and `Formula/curio.rb` in `samsar/homebrew-tap`. Every action is pinned by commit SHA with the tag in a trailing comment; Dependabot (`.github/dependabot.yml`) bumps them and the Go modules weekly. cgo limits us to `darwin/arm64` for now (single macos-14 runner). Adding amd64 or linux means matrix runners + `goreleaser --split`/`--merge`; deliberately deferred. See `docs/decisions.md` "Releases: gated on CI, pinned, least privilege".
